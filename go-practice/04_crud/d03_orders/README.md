# GO-D03 · Заказы — транзакции, rollback и конкуренция

Частичная реализация. Код не собирается из-за неиспользуемой переменной err в GetOrders. Зарегистрирован только GET /orders/{id}, CreateOrder содержит незавершённую попытку транзакции, замена, удаление и подтверждение заказа остаются заглушками. Модели, SQL-схема, запуск и тесты полного контракта сохранены.

Работающий сервис с прямыми HTTP-обработчиками находится в [примере CRUD заметок](../../examples/d01_notes/README.md).

## Первый шаг — создание заказа

Начни с регистрации POST /orders и CreateOrder. Запрос содержит items с product_id и qty. Заказ и все позиции создаются одной транзакцией. Ответ 201 отправляется после успешного Commit. При отказе любой позиции весь заказ откатывается.

После создания переходи к ConfirmOrder — проверка остатков, фиксация цен, списание stock и смена статуса в одной транзакции.

## Рабочий файл

В handler/handler.go уже есть Handler с полем db *sql.DB, конструктор New(db) и сигнатуры шести методов. RegisterRoutes вызывается при создании обработчика.

```go
func (h *Handler) RegisterRoutes(mux *http.ServeMux) {
    // Регистрация маршрутов из HTTP-контракта.
}
```

Каждый метод принимает w http.ResponseWriter и r *http.Request. Читай параметры, выполняй SQL через h.db с r.Context() и отправляй ответ внутри метода. Ошибки отправляй через http.Error, логирование добавляй через log.Printf.

## Таблицы

Готовая схема находится в schema.sql. Тесты создают товары напрямую через SQL.

| Таблица | Поля и ограничения |
|---|---|
| products | id BIGSERIAL PRIMARY KEY, name TEXT NOT NULL, price_cents BIGINT NOT NULL CHECK >= 0, stock BIGINT NOT NULL CHECK >= 0 |
| orders | id BIGSERIAL PRIMARY KEY, status TEXT NOT NULL DEFAULT 'draft', CHECK status IN ('draft','confirmed') |
| order_items | order_id BIGINT REFERENCES orders(id) ON DELETE CASCADE, product_id BIGINT REFERENCES products(id), qty BIGINT NOT NULL CHECK > 0, price_cents BIGINT NULL CHECK >= 0, PRIMARY KEY(order_id, product_id) |

При удалении товара, на который есть ссылка, действует ограничение FK. Цена позиции черновика равна NULL. Подтверждение сохраняет текущую цену товара в order_items.price_cents.

## JSON

Запрос создания и полной замены позиций

```json
{"items":[{"product_id":1,"qty":2},{"product_id":2,"qty":1}]}
```

Ответ

```json
{
  "id": 1,
  "status": "draft",
  "items": [
    {"product_id": 1, "qty": 2, "price_cents": null},
    {"product_id": 2, "qty": 1, "price_cents": null}
  ]
}
```

Позиции в ответе сортируются по product_id. После подтверждения status становится confirmed, цены становятся числами.

## Ручки

| Запрос | Успех |
|---|---|
| POST /orders | 201 и созданный черновик с позициями |
| GET /orders/{id} | 200 и заказ с позициями |
| GET /orders | 200 и массив заказов по id, каждый с позициями |
| PUT /orders/{id} | 200 и черновик с полностью заменёнными позициями |
| DELETE /orders/{id} | 204, заказ и позиции удалены |
| POST /orders/{id}/confirm | 200 и подтверждённый заказ |

В заказе минимум одна позиция. product_id и qty положительные, product_id внутри одного запроса уникален. Пустой список заказов возвращается как [].

## Транзакции

Создание, замена и удаление заказа с позициями атомарны. Подтверждение в одной транзакции проверяет состояние заказа и остатки, фиксирует цены, списывает stock и меняет статус. Используй BeginTx, tx.Query/Exec с контекстом, Commit и Rollback. Успех отправляется после успешного Commit.

При нехватке любого товара все остатки, позиции и статус сохраняют исходное состояние. Повторный confirm возвращает подтверждённый заказ с сохранёнными ценами. Два confirm одного заказа списывают остатки один раз. Два разных заказа на последнюю единицу товара дают ровно один успех. При нескольких товарах захватывай блокировки в согласованном порядке product_id.

Подтверждённый заказ доступен для чтения. PUT и DELETE такого заказа возвращают 409.

## Ошибки

- 400 при пустом items, повторном product_id, неположительных product_id или qty и ошибке декодирования JSON.
- 404 для отсутствующего заказа.
- 409 при отсутствующем товаре, нехватке остатка, изменении или удалении confirmed-заказа.
- 500 при внутренней ошибке, включая отказ Commit.

После отказа состояние БД соответствует состоянию до запроса. Отмена HTTP-запроса отменяет ожидающий SQL и откатывает транзакцию. Пул сохраняет пригодность для следующих запросов.

## Проверки

```sh
export TEST_DATABASE_URL='postgres://student@127.0.0.1:15432/go_interview_orders?sslmode=disable'
go test -timeout=30s -v ./04_crud/d03_orders/handler
go test -timeout=30s -race -count=1 ./04_crud/d03_orders/handler
```

Тесты работают через HTTP и настоящую PostgreSQL в автоматически удаляемых схемах. Кроме CRUD, проверяются rollback после отказа второй позиции, цены, повторный confirm, конкурентные confirm, отмена заблокированного SQL и отказ Commit через отложенный триггер внутри тестовой схемы.

## Запуск

После исправления сборки создай базу go_interview_orders на локальном PostgreSQL с портом 15432 и примени schema.sql. Сервер запускается из корня go-practice.

```sh
go run ./04_crud/d03_orders/cmd/server
```

По умолчанию сервер слушает 127.0.0.1:8085 и ожидает базу go_interview_orders на 127.0.0.1:15432 под пользователем student. DATABASE_URL и HTTP_ADDR позволяют задать свои значения.

В cmd/server/main.go уже выполнены sql.Open, PingContext, настройка пула, HTTP-таймаутов и остановки по Ctrl+C/SIGTERM. Тесты создают отдельные временные схемы и применяют готовый schema.sql.

Существующие тесты можно выполнить после исправления сборки. Они задают ожидаемые результаты для завершения обработчиков и регистрации маршрутов.
